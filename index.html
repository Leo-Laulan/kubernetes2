Linux, Conteneurs & OCI Cours 1
  • Namespaces (Isolation logique) :
    - UTS : nodename et nom d'hôte isolés (uname/hostname).
    - PID : permet d'avoir un processus init propre (PID 1).
    - Mount : vue distincte de la hiérarchie du système de fichiers.
    - IPC : mémoire partagée et sémaphores isolés.
  • Cgroups (Groupes de contrôle) : allocation et bridage matériel (CPU, RAM, bande passante réseau, I/O disque).
  • Securite :
    - SELinux : contrôle d'accès obligatoire (MAC).
    - Seccomp : restriction des appels système noyau (le profil Docker désactive environ 44 appels système sur plus de 300).
  • Docker vs Podman : Podman est daemonless (sans démon résident, lancé directement par runC) et supporte le mode rootless. Docker dépend du démon central `dockerd`.
Control Plane & Kubeconfig Cours 1
  • etcd & Consensus RAFT : magasin clé-valeur distribué, unique source de vérité. Trois rôles de nœud possibles : Leader (unique dans un cluster sain), Follower, et Candidat (état transitoire lors d'une élection).
  • API Server (kube-apiserver) : point d'entrée unique REST (CRUD). Seul composant dialoguant directement avec etcd. Pipeline d'exécution : Authentification -> Autorisation -> Contrôle d'admission -> Validation.
  • Scheduler : détecte les pods sans nœud et décide où les affecter selon les ressources, contraintes et affinités.
  • Controller Manager : boucle continue de réconciliation (état réel = état désiré). Il délègue l'action à l'API Server sans toucher lui-même aux machines.
  • Composants du Worker Node :
    - Kubelet : agent du nœud, reçoit les ordres de l'API Server et pilote le runtime local.
    - cAdvisor : collecte et agrège les métriques de consommation (CPU, RAM) des conteneurs.
    - Kube-proxy : configure les règles réseau locales pour les Services.
  • Fichier Kubeconfig : cherché par défaut dans $HOME/.kube/config. Modifiable via la variable d'environnement KUBECONFIG ou le drapeau --kubeconfig.
Pods & Types de Workloads Cours 2
  • Cycle de vie du Pod :
    - Pending : accepté par K8s, inclut le temps d'assignation et le téléchargement des images conteneur.
    - Running : assigné à un nœud et au moins un conteneur tourne ou démarre.
    - Succeeded : conteneurs terminés avec succès (code retour 0), aucun redémarrage.
    - Failed : au moins un conteneur a terminé avec un code non nul ou a été stoppé.
    - Unknown : communication rompue avec l'hôte du pod.
  • Nature du Pod : entité éphémère dotée d'un UID unique. Un pod mort n'est jamais réordonnancé ; il est remplacé avec un nouvel UID.
  • Les 5 types de Workloads :
    - Deployment : applications sans état (stateless), gère les ReplicaSets.
    - StatefulSet : applications avec état (bases de données nécessitant des identifiants stables et du stockage persistant).
    - DaemonSet : assure qu'une copie du pod s'exécute sur chaque nœud du cluster (collecte de logs, agents réseau).
    - Job : exécute des pods jusqu'à terminaison complète avec succès (batch processing, migrations).
    - CronJob : exécute un Job de manière périodique selon un planning cron.
ReplicaSets & Deployments TP1 Majeur
  • ReplicaSet : maintient un compte stable de pods identiques.
    - Piège : le filtrage s'opère uniquement via les labels (`matchLabels`). Si un pod tiers a le même label, le ReplicaSet détruit l'excédent.
  • Stratégies de mise à jour natives :
    - RollingUpdate (défaut) : remplacement progressif sans coupure. Paramétré par maxSurge (dépassement autorisé au-dessus du quota, défaut 25%) et maxUnavailable (indisponibilité temporaire tolérée, défaut 25%).
    - Recreate : stoppe simultanément l'ensemble des anciens pods avant de lancer les nouveaux (provoque une coupure de service).
  • Rollback : commande `kubectl rollout undo deployment/ --to-revision=`. En cas d'image erronée (`ImagePullBackOff`), les anciens pods restent actifs pour garantir la disponibilité.
Stratégies Avancées (Canary vs A/B) Cours 2
  • Blue/Green : deux déploiements complets tournent en parallèle (Blue en production, Green en test). La bascule de trafic est instantanée mais coûte le double de ressources.
  • Canary (Technique) : envoi progressif d'un faible pourcentage de trafic réel sur la nouvelle version. On observe les métriques techniques (taux de codes HTTP 200 vs 5xx) avant d'étendre la diffusion.
  • Tests A/B (Métier / Produit) : division des utilisateurs en deux groupes distincts (groupe témoin A vs groupe de traitement B) selon des critères précis (en-têtes HTTP, cookies, localisation). Nécessite un proxy de niveau 7 (L7).
Services Réseau & Limitations Cours 2 & TP2
  • Les 4 types de Services :
    - ClusterIP (défaut) : IP interne non accessible hors du cluster. Idéal pour sécuriser les bases de données (Redis backend).
    - NodePort : ouvre un port statique sur chaque nœud (plage 30000-32767). Crée un ClusterIP sous-jacent.
    - LoadBalancer : provisionne un répartiteur chez un fournisseur Cloud (L4 ou L7).
    - ExternalName : mappe le service sur un enregistrement DNS externe (CNAME). Ne configure aucun proxy ni IP.
  • Limitations du LoadBalancer natif :
    - Ne gère que des adresses IP, pas des noms de domaine.
    - Exige un équilibreur payant par service exposé, ce qui devient coûteux et complexe à maintenir.
  • Endpoints : ressource interne listant les couples IP:Port des pods sains correspondant aux labels du sélecteur.
Ingress & Gateway API Cours 2 & TP2
  • Ingress classique : point d'entrée HTTP/HTTPS unique gérant l'hébergement virtuel basé sur le nom et la terminaison TLS. Supporte le Fanout (routage par chemin d'URL vers différents services, ex: `/foo` vers service1, `/bar` vers service2).
  • Gateway API (Modèle orienté rôles) :
    - GatewayClass : géré par l'infrastructure (ex: `kgateway.dev/kgateway`).
    - Gateway : géré par les administrateurs du cluster (ex: `main-gateway` dans `infra-gateway`).
    - HTTPRoute : géré par le développeur dans son namespace personnel.
  • Implémentation kgateway :
    - Control Plane : déploiement `kgateway` dans `kgateway-system`.
    - Data Plane : proxy Envoy déployé dans `infra-gateway`.
  • Diagnostic d'une HTTPRoute :
    - `Accepted: True` : la route est validée par la Gateway parente.
    - `ResolvedRefs: False` (Reason: `BackendNotFound`) : le service cible dans `backendRefs` est introuvable. Envoy renvoie un code HTTP 500 ou 503.
Structure Fichier YAML K8s Syntaxe DS
  • 4 Clés Obligatoires de 1er niveau :
    - apiVersion : version de l'API (ex: `v1` pour Pod/Service/Namespace, `apps/v1` pour Deployment/ReplicaSet, `gateway.networking.k8s.io/v1` pour HTTPRoute).
    - kind : type d'objet instancié (ex: Pod, Deployment, Service).
    - metadata : description de l'objet (name, namespace, labels, annotations).
    - spec : spécification technique détaillée de l'état souhaité (replicas, selector, template, ports).
